## What the controller does
Drives camera-relative locomotion for a `CharacterController` on the Player prefab. Per frame it reads `Move`/`Sprint`, builds a camera-flattened direction, smooth-rotates a child `Pivot` (root stays unrotated so the Cinemachine camera stays stable — a good decision), applies gravity, drives an Animator `Speed` float, handles `Attack` via input callback, and exposes `PlayFootStep()` for Animation Events. It has XML docs, cached components, no per-frame allocs, no per-frame `GetComponent`.

Honest verdict: **better than "messy"** — the real problems are (a) dead debug scaffolding, (b) responsibility creep the author already TODO'd, and (c) a project-level duplicated-input issue this file participates in but didn't cause.

- **P3 — `Awake` silently overwrites Inspector Animator.** `:68` `GetComponent<Animator>()` (not `GetComponentInChildren`, no null guard) contradicts its own tooltip at `:31`. Latent today (prefab puts Animator on root) but breaks if rig moves under a child or field is hand-assigned. Siblings `ResolveCameraTransform()`/`ResolveModelPivot()` do this correctly with guards+warnings.

## Recommended approach (matched to existing project patterns)
The project already owns both patterns needed — `GameplayEventBus` (`Assets/Scripts/Events/GameplayEventBus.cs:10`) and a player-agnostic `StateMachine`/`State` (`Assets/Scripts/Enemy/StateMachine.cs:12`). Nothing new to invent.

Tiering (do NOT implement now — document only):
- **Tier 0 (pure cleanup, no behavior change):** delete `:42–54` spike block + `jump.cs`; drop always-true `:83` test; collapse `ApplyGravity` double-assign; replace `:107` sqrt with known scalar; hash `Attack` trigger; guard Animator resolve at `:68` to match tooltip.
- **Tier 1 (one shared input owner):** single `PlayerInputProvider` MonoBehaviour owning one `PlayerControls`, exposing `Move`/`SprintHeld` + `Attack`/`Interact` events. `ThirdPersonController`, `PlayerInteractor`, `UIController` take it via `[SerializeField]`+`[RequireComponent]`. Prefer serialized ref over singleton (two consumers already on same GameObject — KISS, testable, leaves room for 2nd player).
- **Tier 2 (split responsibilities):** `PlayerLocomotion` (input→direction→gravity→Move, keep pivot rotation), `PlayerAnimationDriver` (owns all Animator hashes), `PlayerFootstepAudio` (the Animation Event target — re-point `Walk_Loop.anim`/`Run_Loop.anim` events), `PlayerCombat` (the TODO class).

Explicitly recommended NOT to do yet:
- **No state machine** — only 2 effective states (idle/moving), no jump/dodge/stagger. Wait for the 3rd real state; then promote the existing `StateMachine` to `Dungeon.Core` rather than writing a second one.
- **Don't put locomotion on the event bus** — per-frame movement must not raise events. Bus is for discrete multi-listener facts (`PlayerAttackedEvent`).
